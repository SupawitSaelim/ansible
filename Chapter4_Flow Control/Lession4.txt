Flow Control
Loops
 - Loops allow running the same task multiple times with different values.
 - They make playbooks more compact, flexible, and easier to maintain.
 - The current iteration value is stored in the item variable.
 - You can loop over lists, dictionaries (using dict2items), or hashes.
 - Use loop_control.loop_var to rename item when using nested loops.

Registering Variables
 - Use the register keyword to capture the output of a task into a variable.
 - The registered variable contains details like stdout, stderr, rc (return code), etc.
 - You can access these details using dot notation (e.g., myvar.stdout).
 - Registered variables can be used in subsequent tasks for conditional execution or reporting.

Pausing
 - The pause module allows you to pause playbook execution for a specified duration or until user input.
 - You can specify the duration in seconds using the seconds parameter.
 - The prompt parameter can be used to display a message to the user during the pause.
 - This is useful for waiting for external processes or for user confirmation before proceeding.

Indexing
 - Use loop_control.index_var to store the current loop index in a custom variable.
 - This variable can be referenced inside tasks to display or use the iteration number.

Special Variables
 - Ansible provides special variables related to hosts and loops.
 - ansible_play_hosts, ansible_play_batch, and groups hold host lists that can be used in loops.
 - Example: loop: "{{ groups['therock'] }}" prints all hosts in a specific group.
 - The query('inventory_hostnames', pattern) function retrieves hosts dynamically from inventory.
 - With loop_control: extended: true, Ansible exposes loop metadata variables (e.g., ansible_loop.index, ansible_loop.first, ansible_loop.last) for advanced control.

Retrying Tasks Until a Condition Is Met
 - Ansible can retry tasks automatically until a specific condition is satisfied.
 - Use until, retries, and delay to define the condition, number of attempts, and waiting time.
 - Example: retry a task up to 5 times, waiting 10 seconds each time, until output contains “succeeded.”
 - If the condition becomes true, Ansible stops retrying early.
 - Best used with idempotent modules, since repeated execution of non-idempotent ones may cause inconsistent states.

Conditionals
 - Ansible uses conditionals with the when directive to control task execution.
 - Tasks can run selectively based on facts, variables, or registered results.
 - Useful when managing multiple OS types (e.g., Fedora vs Debian) with different package managers.
 - You can store facts in variables (set_fact) to simplify and reuse conditional logic.
 - Conditional expressions support all Jinja2 tests and filters.

Ninja2
 - Jinja2 expressions in conditionals are evaluated as Python expressions.
 - Use logical operators (and, or, not) to combine multiple conditions.
 - Here are the conditionals for comparing elements: ==, !=, <, >, <=, >=, in, is.
 - Example: when: ansible_facts['os_family'] == "RedHat" and ansible_facts['distribution_major_version'] | int >= 8

Handlers
 - Handlers are special tasks that run only when notified by other tasks.
 - They are typically used for actions like restarting services after configuration changes.
 - Handlers are defined in a separate section and can be notified using the notify keyword.
 - Handlers run at the end of a play, ensuring that all changes are applied before restarting services.
 - You can notify multiple handlers from a single task, and handlers can also notify other handlers.

Error management
 - Ignoring Failed Commands
   - Use ignore_errors: yes to continue playbook execution even if a task fails.
   - This is useful for non-critical tasks where failure should not halt the entire playbook.
   - Even though the first command fails, the second command runs too.
 - Defining Failure
  - Use failed_when to define custom failure conditions for tasks.
  - This allows you to specify when a task should be considered failed based on its output or other criteria.
  - Example: failed_when: "'Error' in myvar.stdout" marks the task as failed if "Error" is found in the output.
 - Defining Change
  - Use changed_when to define when a task should be marked as changed.
  - This is useful for tasks that may not always result in a change, allowing for more accurate reporting.
  - Example: changed_when: "'Success' in myvar.stdout" marks the task as changed if "Success" is found in the output.
 - Aborting a Play
  - any_errors_fatal can be set to true at the play level to abort the entire play if any task fails.
  - This is useful for critical plays where failure of any task should stop further execution.
  - Example: any_errors_fatal: true ensures that if any task fails, the play stops immediately.

Blocks
Grouping Tasks with Blocks
 - Blocks allow you to group multiple tasks together for better organization and error handling.
 - You can apply directives like when, become, ignore_errors, etc., to the entire block instead of individual tasks.
 - Blocks can contain tasks, handlers, and even other blocks.
Error Handling with Blocks
 - Use rescue and always sections within a block to handle errors gracefully.
 - The rescue section runs if any task in the block fails, allowing you to define fallback actions.
 - The always section runs regardless of success or failure, useful for cleanup tasks.
